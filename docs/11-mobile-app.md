# 11 — Mobile Application

> წყარო: PRD §81, §83, §98, §45, §49, §55. სტეკი: React Native + Expo + TypeScript.

---

## 1. UX-ის მთავარი წესი (§45)

> აპლიკაცია არ უნდა იყოს ტექნიკური.

მომხმარებელს **არასოდეს** ვთხოვთ იცოდეს: OEM · SKU · engine code · part number.

```
ის ამბობს:       „მჭირდება BMW-ს საქარე მინა.“
სისტემა აკეთებს: VIN → კონფიგურაცია → fitment → OEM → offers
```

OEM და part number **ჩანს** პროდუქტის გვერდზე (§54) — როგორც ინფორმაცია მათთვის, ვისაც
სჭირდება. მაგრამ ისინი არასოდეს არის **საჭირო** ყიდვისთვის.

## 4. Add Vehicle

```
VIN (17 სიმბოლო)        [📷 სკანირება]
┌──────────────────────────────────┐
│ W B A 1 J 5 C 5 0 F V _ _ _ _ _ _│
└──────────────────────────────────┘
```

**კლიენტის მხარეს ვალიდაცია (§8):** სიგრძე · დაშვებული სიმბოლოები (I, O, Q არ არსებობს
VIN-ში) · checksum იქ, სადაც სტანდარტი იძლევა. სერვერამდე მისვლა მხოლოდ სტრუქტურულად
სწორ VIN-ზე — provider-ის გამოძახება ფულს ღირს.

**კამერით სკანირება** — VIN ჩვეულებრივ საქარე მინის ქვეშ ან კარის ჩარჩოზეა. OCR + manual
რედაქტირება.

### 4.1 დადასტურება
```
ვიპოვეთ თქვენი ავტომობილი

BMW 2 Series · 228i
2016 · F22 · 2.0 Turbo (N20B20)
ავტომატური · უკანა წამყვანი · ბაზარი: US

[სწორია, დამატება]   [ეს ჩემი მანქანა არ არის]
```

### 4.2 დამაზუსტებელი კითხვა (§10)
```
კიდევ ერთი კითხვა

თქვენს ავტომობილს აქვს 2 განსხვავებული
სამუხრუჭე კონფიგურაცია. აირჩიეთ შესაბამისი:

  ○ სტანდარტული
  ○ M Sport

ℹ️ ეს დაგვეხმარება ზუსტი ნაწილების ჩვენებაში.
   [არ ვიცი] — მოგვიანებით დავაზუსტებთ.
```

**„არ ვიცი“ ყოველთვის ხელმისაწვდომია.** მისი არჩევისას პასუხი არ ინახება და
ამ ატრიბუტზე დამოკიდებული პროდუქტები `UNCERTAIN`-ად რჩება (ანუ არ ჩანს).
მომხმარებლის იძულება, უპასუხოს იმას, რაც არ იცის, არასწორ `user_supplied_data`-ს
წარმოშობს — და ეს პირდაპირ აზიანებს Fitment Accuracy-ს.

### 4.3 VIN ვერ იშიფრა (§43 v1)
```
ვერ მოვახერხეთ თქვენი ავტომობილის ამოცნობა

[თავიდან ცდა]   [ხელით შეყვანა]
```
ხელით შეყვანა: make → model → year → engine → transmission.
შედეგი მიდის `user_supplied_data`-ში, `verified_data` ცარიელი რჩება — და ძრავა
ამას ითვალისწინებს ([05 §5](05-fitment-engine.md), `× 0.8`).

```

  რაოდენობა · გამყიდველი · აღების მისამართი · სამუშაო საათები
  ფასი · ჯამი · გაუქმების წესები · დაბრუნების წესები · გადახდის პირობები

     ↓
```

**რეზერვაციის ტაიმერი ხილულია.** მომხმარებელმა უნდა იცოდეს, რომ დრო შეზღუდულია —
თორემ ვადის გასვლა მოულოდნელი შეცდომაა.

## 8. Notifications (§78)

| ტიპი | არხი |
|------|------|
| Order confirmation | Push + In-app |
| Payment confirmation | Push + In-app |
| **Ready for pickup** | Push + SMS + In-app |
| Cancellation | Push + SMS |
| Refund | Push + Email |
| Request Part response *(P1)* | Push + In-app |

Ready-for-pickup და cancellation SMS-ითაც იგზავნება — push შეიძლება გამორთული იყოს,
ეს ორი კი ქმედებას მოითხოვს.

## 9. ტექნიკური

| თემა | გადაწყვეტა |
|------|------------|
| Navigation | React Navigation, deep links (`autoparts://order/…`) |
| State | TanStack Query (server) + Zustand (UI) |
| API | `packages/api-client` — OpenAPI-დან გენერირებული |
| Offline | Garage, შეკვეთების ისტორია და კატეგორიები ქეშირდება; ძებნა და offers — **არასოდეს** |
| i18n | `packages/i18n`, ka/en, device locale-ით (§80) |
| Secure storage | Keychain / Keystore — tokens |
| Push | Expo Notifications → APNs/FCM |
| ფული | `bigint` minor units, ფორმატირება `Intl.NumberFormat`-ით |
| ხელმისაწვდომობა | მინ. 44pt touch target, dynamic type, VoiceOver/TalkBack |

**რატომ არ ქეშირდება offers offline:** ქეშირებული ფასი და მარაგი R2-ის დარღვევაა.
მოძველებული „In Stock“ უარესია, ვიდრე ცარიელი ეკრანი „ინტერნეტი არ არის“.
