# 10 — Partner Portal

> წყარო: PRD §56, §99, §24–25, §38–39, §48. აპლიკაცია: `apps/partner` (Next.js).
> წვდომა: `PARTNER_USER` / `PARTNER_ADMIN`.

---

## 1. დანიშნულება

პარტნიორისთვის ეს არის **დამატებითი გაყიდვების არხი**, არა ახალი სამუშაო ადგილი.
თუ ყოველდღიური მუშაობა 10 წუთზე მეტს წაიღებს, პარტნიორი შეწყვეტს გამოყენებას და
marketplace დაიცლება.

ამიტომ პორტალის დიზაინის წესი: **ყოველდღიური სამუშაო = შეკვეთების ნახვა და
„Ready for Pickup“-ის დაჭერა.** ყველაფერი დანარჩენი — მარაგი, ფასები, ინტეგრაცია —
იშვიათი ან ავტომატურია.

## 4. Orders — მთავარი ეკრანი

```
┌──────────────────────────────────────────────────────────────┐
│ AP-10234        გადახდილი        15 სექ, 14:22               │
│ Front Brake Pads — Bosch 0986424815 · 1 ცალი                 │
│ მანქანა: BMW 2 Series · 2016 · 2.0 Turbo                     │
│ ფილიალი: ვაჟა-ფშაველას 12                                    │
│ თანხა: 500.00 ₾                                              │
│                              [მზადაა ასაღებად]               │
└──────────────────────────────────────────────────────────────┘
```

| ველი | ჩანს? | მიზეზი |
|------|:-----:|--------|
| მომხმარებლის სახელი + ტელეფონი | ✅ | pickup-ისთვის საჭიროა |
| მანქანის make/model/year/engine | ✅ | სწორი ნაწილის მოსამზადებლად |
| **VIN** | ❌ | §76 — VIN არ არის საჯარო; პარტნიორს არ სჭირდება |
| `base_price` (500 ₾) | ✅ | ეს მისი ფულია |
| `customer_price` (550 ₾) | ✅ | იცოდეს რა ფასად იყიდება |
| **markup-ის პროცენტი** | ❌ | კომერციული პირობა, admin-ის კონტროლში |
| **სხვა პარტნიორის ფასი** | ❌ | §3, §31 — აღსრულებულია query-ის დონეზე |

### 4.1 Ready for Pickup (§48)

```
[მზადაა ასაღებად] →  ready_for_pickup_at = now()
                  →  pickup_deadline     = now() + 24სთ
                  →  Customer notification: „თქვენი შეკვეთა მზადაა ასაღებად“
                  →  24-საათიანი ტაიმერი ჩანს ორივე მხარეს
```

**გაფრთხილება ეკრანზე:** „თუ მომხმარებელი 24 საათში არ მოვა, შეკვეთა ავტომატურად
გაუქმდება და თანხა დაუბრუნდება.“ (§52) პარტნიორმა ეს წინასწარ უნდა იცოდეს.

### 4.2 Pickup verification (§49)

```
მომხმარებელი აჩვენებს QR-ს
        ↓
პარტნიორი სკანირებს (dashboard-ის კამერით ან ხელით კოდის შეყვანით)
        ↓
POST /partner/orders/:id/verify-pickup
        ↓
✅ დადასტურებულია → PICKED_UP
```

QR payload — ერთჯერადი ხელმოწერილი ტოკენი, არა order ID. ვადა: `pickup_deadline`-მდე.
**Fallback:** თუ კამერა არ მუშაობს ან მომხმარებელს ტელეფონი გამოეთიშა — 6-ნიშნა
კოდი ხელით. QR ვერასოდეს უნდა იყოს ერთადერთი გზა.

**საბოლოო `COMPLETED` დგება მომხმარებლის დადასტურებით (§50)** — პარტნიორის
verify-pickup ამას წინ უსწრებს, მაგრამ არ ცვლის.

## 5. Products & Inventory

### 5.1 სამი რეჟიმი (§24, [ADR-006](00-index-and-decisions.md))

| Manual | CSV | API |
|--------|-----|-----|
| ხელით dashboard-იდან | ფაილის ატვირთვა | ERP-ის ინტეგრაცია |
| პირველი პარტნიორები | საშუალო ზომის | დილერები |

### 5.2 Add Product ფორმა

**სავალდებულო (§25):** SKU · OEM/Part Number · Product Name · Brand · Price · Stock ·
Availability
**სასურველი:** Fitment · Technical data · Images · Warranty · Expected availability

**Fitment-ის ველი განსაკუთრებულია.** ფორმაზე პირდაპირ წერია:

> ℹ️ თქვენს მიერ მითითებული თავსებადობა გადამოწმდება პლატფორმის Fitment Engine-ით.
> შეუსაბამობის შემთხვევაში პროდუქტი დროებით დაიმალება, სანამ ადმინი არ გადაამოწმებს.

ეს R3-ის (§97) გამჭვირვალე გადმოცემაა. პარტნიორმა უნდა იცოდეს, რომ მისი მტკიცება
სიგნალია და არა საბოლოო სიტყვა — თორემ პროდუქტის გაუჩინარება მისთვის ბაგად აღიქმება.

### 5.3 CSV Import (§57)

```
[შაბლონის ჩამოტვირთვა]  ←  ყოველთვის ხელმისაწვდომი, 2 მაგალითი row-ით

Upload → Validate → Normalize → Match → Fitment → Import
```
```
✅ 1,198 ჩაიტვირთა
❌ 52 შეცდომა                          [შეცდომების ჩამოტვირთვა CSV-ად]
   row 17 · price  · უარყოფითი ფასი: -40
   row 23 · oem    · არასწორი OEM ფორმატი: "??"
   row 88 · sku    · გამეორებული SKU ფაილში: BP-2211
```
**Partial import სტანდარტია:** სწორი row-ები შედის, არასწორი — არა. „ყველაფერი ან
არაფერი“ ნიშნავს, რომ 1 შეცდომა 1,200 პროდუქტს აჩერებს.

## 7. Locations

ფილიალი სავალდებულოა — pickup-ის გარეშე შეკვეთა ვერ შესრულდება.

ველები: სახელი · მისამართი · ქალაქი · კოორდინატები (რუკაზე მონიშვნა) ·
სამუშაო საათები · pickup instructions · ტელეფონი · აქტიური.

**კოორდინატები საჭიროა `Nearest` sorting-ისთვის (§34).** მისამართის ტექსტი საკმარისი
არ არის — გეოკოდირება ხდება შენახვისას, და ადმინს შეუძლია ხელით შესწორება.

## 9. რას ხედავს პარტნიორი საკუთარ თავზე

გამჭვირვალობა განზრახია — რაც პარტნიორს ვუჩვენებთ, იმას ის აუმჯობესებს:

| მეტრიკა | რატომ ჩანს |
|---------|-----------|
| Stock Reliability Score | პირდაპირ მოქმედებს Recommended ranking-ზე (§35) |
| Sync health + ბოლო განახლება | მოძველებული მარაგი = გაუქმებული შეკვეთები |
| Cancellation rate | თვითკონტროლი |
| საშუალო ready-for-pickup დრო | კონკურენტული უპირატესობა |
| Fitment conflicts მის პროდუქტებზე | იცოდეს **რატომ** არ ჩანს მისი პროდუქტი |

ბოლო სტრიქონი განსაკუთრებით მნიშვნელოვანია: პროდუქტის ჩუმად გაუჩინარება პარტნიორისთვის
პლატფორმის ბაგია. კონფლიქტის ჩვენება მას ახსნად აქცევს.
